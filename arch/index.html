Хранение данных

Где хранить базу данных?

Всё на одной машине

Учебный проект
  • Flask-приложение и файл SQLite в одной папке
  • Нормально для ноутбука и учебной аудитории
  • Просто, быстро, не требует инфраструктуры
  • Но: любая уязвимость в веб-приложении ставит под угрозу всю базу

Разделение на серверы

Реальная система
  • Веб-приложение — на одном узле
  • База данных — на другом
  • Соединение строго контролируется
  • Веб-сервер не имеет прямого доступа к файловой системе БД
  • Общение — только через сетевой порт и разрешённые учётные данные

Принцип наименьшего привилегированного доступа: если база и веб-сервер на одной машине, злоумышленник, получивший доступ через дыру в Flask, получает и доступ к данным. Изоляция — первый уровень защиты.

Хранение данных

Изоляция и юрисдикция

  • 1Изоляция. Веб-сервер общается с БД только по сети, через порт, с определёнными учётными данными. Нет прямого доступа к файлам.
  • 2Локализация (152-ФЗ). Базы с персональными данными российских граждан должны физически находиться на территории РФ.
  • 3Это не юридическая формальность, а архитектурное ограничение.
  • 4Для учебного проекта — локально или на учебном сервере, но принцип разделения закладываем в документацию.

Два вопроса при выборе места

Достаточно ли оно изолировано от веб-приложения? И находится ли оно в правильной юрисдикции?

Это покажет, что вы понимаете разницу между «работает на ноутбуке» и «работает в продакшене».

Резервное копирование

Данные — самый ценный актив

Код можно переписать, сервер — пересоздать. Но если потеряна база с заказами или учётными записями, бизнес может просто остановиться. Резервное копирование — не «хорошая практика», а обязательное требование.

Полное

Копируется всё целиком. Надёжно, но долго и требует много места.

Инкрементное

Только изменения с момента последнего копирования. Быстро, но восстановление сложнее — цепочка копий.

Дифференциальное

Изменения с момента последнего полного копирования. Компромисс между скоростью и сложностью.

Главное: резервная копия, которую никто никогда не пробовал восстановить, — это не резервная копия, а просто файл, который занимает место. Вы должны уметь ответить: «Если завтра сервер сгорит, за сколько времени мы восстановим данные и насколько полно?»

Резервное копирование · SQLite

Просто скопировать файл — не всегда безопасно

SQLite хранит всю базу в одном файле. Это одновременно преимущество и ловушка.

Преимущество

Резервная копия — простое копирование файла.

Ловушка

Если скопировать файл в момент записи — копия может оказаться повреждённой. «Половина» транзакции.

Для согласованной копии при работающем приложении существуют специальные команды: .backup в командной строке или функция backup в Python.

# согласованная резервная копия SQLite import sqlite3 src = sqlite3.connect("app.db") dst = sqlite3.connect("backup.db") # копирует даже при активных записях src.backup(dst) dst.close() src.close() # в документации: для реальной системы # нужен автоматизированный механизм # с проверкой целостности
Резервное копирование · MySQL

Логический дамп и репликация

MySQL — серверная СУБД. Здесь недостаточно скопировать файлы: данные хранятся в нескольких файлах и используются журналы транзакций.

  • 1mysqldump — логическая копия: набор SQL-команд, восстанавливающих базу.
  • 2Дамп можно сжать, зашифровать и передать по сети.
  • 3Нюанс: mysqldump может блокировать таблицы на время создания дампа.
  • 4Поэтому в реальных системах делают дампы с реплики, а не с основного сервера.
# логический дамп базы mysqldump -u app_user -p \ --single-transaction \ --routines --triggers \ app_db > backup.sql # сжатие и шифрование gzip -c backup.sql | \ openssl enc -aes-256-cbc \ -out backup.sql.gz.enc # восстановление gunzip -c backup.sql.gz | \ mysql -u app_user -p app_db

Архитектурный приём: разделение нагрузки между записью и чтением — дампы снимаются с реплики, основной сервер продолжает обслуживать пользователей.

Копии тоже содержат персональные данные

Шифрование

Нельзя хранить копии в открытом виде на общедоступном диске.

Ограничение доступа

Только те, кому это действительно необходимо.

Учёт носителей

Внешние носители должны быть учтены и защищены.

Политика хранения

Как часто, где, как долго, кто имеет доступ.

Это не мелочи: утечка резервной копии — это такая же утечка персональных данных, со всеми вытекающими последствиями по 152-ФЗ.

Межсетевой экран между DMZ и внутренней сетью разрешает только строго определённые соединения: например, веб-сервер подключается к базе только по порту MySQL и только с определённого IP. Всё остальное блокируется. Это принцип эшелонированной обороны.

Безопасность · Транспорт

HTTPS и TLS-терминация на прокси

Пользователь должен подключаться по HTTPS, иначе пароль или персональные данные могут быть перехвачены в канале связи.

  • 1Можно настроить на уровне Flask, но правильнее — на уровне обратного прокси (Nginx).
  • 2Nginx принимает HTTPS, расшифровывает и передаёт Flask обычный HTTP внутри защищённого периметра.
  • 3Это разгружает Flask от шифрования и позволяет централизованно управлять сертификатами.
# пример: TLS на Nginx server { listen 443 ssl; server_name app.example.ru; ssl_certificate /etc/ssl/app.crt; ssl_certificate_key /etc/ssl/app.key; location / { proxy_pass http://127.0.0.1:5000; proxy_set_header Host $host; proxy_set_header X-Forwarded-Proto https; } }
Безопасность · Заголовки

HTTP-заголовки, которые защищают браузер

Strict-Transport-Security

Заставляет браузер использовать только HTTPS.

Content-Security-Policy

Ограничивает источники контента, защищает от XSS и подмены.

X-Content-Type-Options

Запрещает браузеру «угадывать» MIME-тип.

Эти заголовки защищают от подмены контента и кликджекинга. Для тестировщика проверка этих заголовков — это отдельный набор тест-кейсов.

Безопасность · Уровень приложения

Управление сессиями

Flask использует подписанные cookie для хранения сессионных данных. Секретный ключ, которым подписываются cookie, должен быть достаточно длинным и случайным.

  • Ключ нельзя хранить в коде или в репозитории
  • Передаётся через переменные окружения
  • Изменяется при развёртывании

Если ключ известен злоумышленнику

Он сможет подделать сессию любого пользователя. Это одна из самых серьёзных уязвимостей. При тестировании проверяйте, что ключ не «зашит» в код и меняется при развёртывании.

Безопасность · Авторизация

Ролевая модель и проверка ограничений

Администратор

Доступ к управлению системой и пользователями.

Обычный пользователь

Доступ только к своим данным и функциям.

Гость

Минимальный доступ, без личных данных.

Тестирование авторизации

Важно не только то, что написано в коде, но и то, как это проверяется. Попробуйте обойти ограничения: может ли обычный пользователь получить доступ к админ-панели, изменив URL? Может ли прочитать чужие данные, подставив другой идентификатор в запрос? Это одна из самых частых дыр в веб-приложениях.

Безопасность · Валидация

Никогда не доверяйте данным от пользователя

Всё, что приходит из формы, из URL, из заголовков, должно быть проверено. Flask и WTForms помогают, но разработчики часто забывают проверять типы данных, длину, формат.

Что может прислать злоумышленник

Строку вместо числа, SQL-код вместо ID, исполняемый файл вместо картинки.

Правило

Валидация на стороне сервера обязательна, даже если она есть на клиенте.

Клиентскую валидацию легко обойти

Она нужна только для удобства пользователя. Все проверки должны дублироваться на сервере — иначе система уязвима.

Безопасность · Наблюдаемость

Логирование и мониторинг

Безопасность — это не только защита, но и обнаружение. Если что-то случилось, вы должны об этом узнать.

01

Что логировать

Все запросы, ошибки, события аутентификации.

02

Чего не должно быть в логах

Паролей, номеров карт, персональных данных в открытом виде.

03

Защита логов

Их нужно отправлять на отдельный сервер, к которому у приложения нет прав на удаление.

Централизованное логирование: если злоумышленник проник в систему, он первым делом попытается замести следы — удалить или изменить логи. Сами по себе записи бесполезны, если их никто не читает: системы мониторинга следят за аномалиями — резкий рост ошибок, множественные неудачные попытки входа, необычные запросы.

Тестирование безопасности

Инструменты и типовые проверки

Проверка архитектуры — это не только чтение документации, но и практические попытки найти слабые места.

OWASP ZAP Burp Suite Анализ запросов Сканирование
  • 1SQL-инъекции — реакция системы на внедрение SQL-кода.
  • 2XSS — межсайтовый скриптинг.
  • 3CSRF — подделка межсайтовых запросов.
  • 4Утечка информации в сообщениях об ошибках.

Защита от перебора

Если при неверном пароле система пишет «Пользователь с таким email не найден» — это подсказка злоумышленнику. Правильнее: «Неверный email или пароль».

Тестирование безопасности

Не «кнопка работает», а «система защищена»

Плохой тест-кейс

«Проверить, что кнопка работает».

Проверяет только функциональность и ничего не говорит о безопасности.

Хороший тест-кейс

«Проверить, что система не позволяет внедрить SQL-код в поле поиска».

«Проверить, что сессионная cookie имеет флаг HttpOnly».

Все эти проверки должны быть частью вашего сквозного проекта. Вы не просто пишете тесты на функциональность — вы проверяете, что система не нарушает права пользователей и не создаёт рисков для бизнеса.
